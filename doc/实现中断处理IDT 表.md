### IDT

GDT 解决了 **“内存段如何隔离和保护”** 的问题，而 IDT 则是为了解决 **“CPU 如何响应突发事件”** 的问题。

没有 IDT，你的内核会面临以下问题：

1. **无法处理 CPU 异常**：比如代码除以 0、访问非法内存（Page Fault）、触发未知指令时，CPU 会因为找不到处理函数直接引发三重故障（Triple Fault）导致虚拟机/电脑重启。
2. **无法响应硬件中断**：比如按下键盘、时钟中断（PIT）、鼠标移动等，CPU 都无法感知。
3. **无法实现系统调用（Syscall）**：用户态程序将来无法通过 `int 0x80` 或 `syscall` 请求内核服务。

## 中断的本质

中断就是：**"硬件/CPU 主动打断 CPU 当前工作，让它跳去执行一段预先注册好的代码"**。

```
CPU 正在执行 A 程序
    ↓
键盘按下 → 产生电信号 → 送到中断控制器 PIC
    ↓
PIC 告诉 CPU："喂，有事！中断号是 33"
    ↓
CPU：好的，我保存现场，去查 IDT[33]
    ↓
IDT[33] 里存着"键盘处理函数的地址"
    ↓
CPU 跳过去执行键盘处理函数
    ↓
处理完，CPU 恢复现场，继续执行 A 程序
```

### 中断的类型

| 类型                   | 来源                 | 举例                 | 中断号                   |
| ---------------------- | -------------------- | -------------------- | ------------------------ |
| **异常（Exception）**  | CPU 内部             | 除以 0、访问非法内存 | 0~31（Intel 规定）       |
| **硬件中断（IRQ）**    | 外部设备             | 键盘、时钟、硬盘     | 可配置（我们设为 32~47） |
| **软中断（Software）** | 程序主动调用 `int N` | 系统调用             | 任意（Linux 用 0x80）    |

```
IDT 表：
┌─────┬────────────────────────────────────┐
│  0  │ 除零异常处理函数地址 + 属性        │
│  1  │ 调试异常处理函数地址 + 属性        │
│ ... │                                    │
│ 14  │ Page Fault 处理函数地址            │
│ ... │                                    │
│ 32  │ 时钟中断处理函数地址（我们定的）   │
│ 33  │ 键盘中断处理函数地址               │
│ ... │                                    │
│ 255 │                                    │
└─────┴────────────────────────────────────┘

CPU 收到中断号 N → 查 IDT[N] → 跳转到那个地址
```

### IDT条目的设置

```
位：  63                48 47 46 45 44 43  40 39   32 31           16 15           0
    ┌─────────────────────┬──┬─────┬──┬──────┬────────┬───────────────┬───────────────┐
    │  处理函数地址高16位 │ P│ DPL │ 0│ Type │ 保留0  │ 代码段选择子  │  处理函数地址 │
    │   (base_high)       │  │     │  │      │(always0)│  (selector)   │ 低16位(base_low)│
    └─────────────────────┴──┴─────┴──┴──────┴────────┴───────────────┴───────────────┘
```

## flags 字段详解

```
flags = 0x8E = 1000 1110
        │  │  │││  ││││
        │  │  ││└──┴┴┴┴── Type: 1110 = 32位中断门（Interrupt Gate）
        │  │  │└───────── 0（保留位）
        │  │  └────────── Storage Segment: 0（固定为0用于中断门）
        │  └─┬──────────── DPL: 00 = 调用者需要 Ring 0 权限
        │    │             (系统调用会设为 11 = Ring 3)
        └────┴──────────── P: 1 = 这个描述符有效
```

**中断门 vs 陷阱门的区别？**

- **中断门 (0xE)**：进入时**自动关中断**（CPU 清 IF 标志）
- **陷阱门 (0xF)**：进入时**不关中断**（可被更高优先级中断打断）

我们选中断门 `0xE`，保证处理中断时不被其他中断干扰。

**段选择子 (Segment Selector) 的结构**：

```
15                3  2  1  0
┌──────────────┬───┬────────┐
│    索引      │TI │  RPL   │
└──────────────┴───┴────────┘

TI  = 0 : 查 GDT (1 查 LDT)
RPL = 0 : Ring 0 权限
索引 = 1 : GDT 中第 1 项
```

所以 `0x08 = 0000 0000 0000 1 0 00`，表示**查 GDT 的第 1 项（内核代码段），Ring 0**。

> 中断发生时，CPU 需要跳转到内核代码执行，所以 selector 必须指向内核代码段。

### IDT存储位置

CPU 内部有个寄存器叫 **IDTR（Interrupt Descriptor Table Register）**，共 48 位：

```
47                16 15        0
┌───────────────────┬───────────┐
│  Base (32位地址)  │ Limit(16) │
└───────────────────┴───────────┘
```

对应结构：

```c
typedef struct {
    uint16_t limit;   // 表的大小 - 1
    uint32_t base;    // 表的起始地址
} __attribute__((packed)) idt_ptr_t;
```

# PIC（可编程中断控制器）详解

## 为什么要有 PIC

CPU 只有 **一根 INTR 引脚**（接收中断信号）和 **一根 NMI 引脚**（不可屏蔽中断）。

但外设有很多！键盘、鼠标、硬盘、网卡、声卡... 怎么办？

**答案：加一个"中介"—— PIC (8259A)**。

```
    键盘 ─┐
    鼠标 ─┤
    硬盘 ─┼─→ [PIC 8259A] ─→ CPU 的 INTR 引脚
    时钟 ─┤
    ...  ─┘
```

PIC 的工作：

1. 收集所有外设的中断信号
2. 按优先级排队
3. 一次发一个给 CPU
4. 告诉 CPU "这是几号中断"

## 主从级联（Master-Slave）

一个 PIC 只有 8 个输入引脚（IRQ0-7），不够用！所以用两片级联：

```
           ┌─ IRQ0  时钟
           ├─ IRQ1  键盘
           ├─ IRQ2  ←──── 从片 PIC ──┬─ IRQ8  实时钟
           ├─ IRQ3  串口              ├─ IRQ9
    主片 ──┤─ IRQ4  串口              ├─ IRQ10
           ├─ IRQ5                    ├─ IRQ11
           ├─ IRQ6  软驱              ├─ IRQ12 鼠标
           └─ IRQ7                    ├─ IRQ13 协处理器
                                      ├─ IRQ14 主硬盘
                                      └─ IRQ15 从硬盘
    ↓
   CPU INTR
```

**从片的输出接到主片的 IRQ2**，所以 IRQ2 实际上不能用于外设。

##  为什么要重映射 PIC？

**问题根源：BIOS 默认让 PIC 发送中断号 0x08~~0x0F（主片）和 0x70~~0x77（从片）。**

但 Intel 规定 **0~31 号留给 CPU 异常**！冲突了！

```
中断号 0x08 到底是：
    - CPU 的 Double Fault 异常？
    - 还是键盘按键？
    CPU 无法分辨！
```

**解决方案：重映射 PIC，让它发送 0x20~~0x2F（32~~47）**。

## 4.5 重映射代码逐行解析

PIC 的初始化需要发送 **4 个初始化命令字 (ICW: Initialization Command Word)**：

```
static void pic_remap(void) {
    // ========== ICW1: 开始初始化 ==========
    outb(0x20, 0x11);   // 主片命令端口 ← 0x11
    outb(0xA0, 0x11);   // 从片命令端口 ← 0x11
    // 0x11 = 0001 0001
    //        │     │
    //        │     └── IC4=1: 需要 ICW4
    //        └──────── 固定位

    // ========== ICW2: 设置中断号基址 ==========
    outb(0x21, 0x20);   // 主片 IRQ0 → 中断号 0x20 (32)
    outb(0xA1, 0x28);   // 从片 IRQ8 → 中断号 0x28 (40)
    // 从此 IRQ0-15 → 中断号 32-47

    // ========== ICW3: 配置级联 ==========
    outb(0x21, 0x04);   // 主片：0x04 = 0000 0100 = IRQ2 位置连接从片
    outb(0xA1, 0x02);   // 从片：告诉自己接在主片 IRQ2 上

    // ========== ICW4: 工作模式 ==========
    outb(0x21, 0x01);   // 0x01 = 8086 模式
    outb(0xA1, 0x01);

    // ========== OCW1: 中断屏蔽寄存器 ==========
    outb(0x21, 0xFF);   // 屏蔽主片所有 IRQ
    outb(0xA1, 0xFF);   // 屏蔽从片所有 IRQ
    // 后面写驱动时按需开启（如键盘：outb(0x21, 0xFD)）
}
```

**为什么开始要全部屏蔽？**

> 防止 IDT 还没完全设置好就来了中断，直接 Triple Fault 重启电脑。

## EOI (End of Interrupt)

**关键机制**：PIC 发送一个中断后，会**挂起不再发送同类中断**，直到你告诉它"处理完了"。

```
void irq_handler(registers_t* regs) {
    // 从片的中断（40-47）需要同时通知主从片
    if (regs->int_no >= 40) {
        outb(0xA0, 0x20);   // 告诉从片：EOI
    }
    outb(0x20, 0x20);       // 告诉主片：EOI
    //        └── 0x20 就是 EOI 命令

    // ... 调用处理函数
}
```

**如果忘记发 EOI 会怎样？**

> 键盘按一次后，再也收不到键盘中断了！（这是新手常见 bug）

# 中断发生时 CPU 到底做了什么？

这是最核心的部分。假设用户按下键盘：

## 5.1 硬件层面

```
1. 键盘控制器检测到按键
2. 发送信号到 PIC 的 IRQ1
3. PIC 查屏蔽寄存器：IRQ1 没被屏蔽 ✓
4. PIC 把中断号 33 (0x21) 放到数据总线
5. PIC 拉高 CPU 的 INTR 引脚
6. CPU 执行完当前指令后，响应中断
```

# 汇编 Stub 的设计艺术

## 6.1 为什么需要 Stub（跳板）

C 函数无法直接作为中断处理函数，原因：

1. **C 函数不会 `pusha`/`popa` 保存现场**
2. **C 函数用 `ret` 返回，但中断必须用 `iret`**
3. **我们需要知道中断号，但 CPU 没告诉 C 函数**

所以必须用汇编写一个"跳板"：

- 保存现场
- 把中断号传给 C
- 调用 C 处理函数
- 恢复现场
- 用 `iret` 返回

# C 层处理函数

## 7.1 两级分发设计

```
中断发生
    ↓
IDT[N] 跳转到 isrN / irqN（汇编）
    ↓
保存现场 → isr_handler / irq_handler（C 总入口）
    ↓
查 interrupt_handlers[N] 表 → 调用注册的具体处理函数
```

**为什么要分两级？**

- 第一级（汇编 stub）：解决栈布局、保存现场
- 第二级（C 总入口）：异常/硬件中断的通用逻辑（如 EOI）
- 第三级（具体 handler）：各驱动自己注册

这是教科书式的"分层设计"。



### 流程

1. **`[SUCCESS] Returned from Interrupt 0x03 safely!`**
   **最硬核的一步**！CPU 查 IDT 表 -> 进汇编 Stub 压栈 -> 跳进 C 语言处理函数 -> 恢复寄存器现场 -> `iret` 指令完美返回 -> 继续执行后面的 C 代码！



## 理论篇：为什么需要 IDT？

在操作系统中，CPU 不能永远只按顺序执行代码。当发生以下三种情况时，CPU 必须立刻放下手中的工作去处理：

1. **CPU 异常 (Exception)**：代码除了 0、访问了非法内存（Page Fault）。
2. **硬件中断 (IRQ)**：用户敲击了键盘、时钟滴答、网卡收到数据。
3. **软中断 (Software Int)**：用户态程序请求内核服务（系统调用，如 `int 0x80`）。

**IDT（中断描述符表）就是 CPU 的“紧急事件电话簿”**。
它是一个有 256 个条目的数组，当第 `N` 号中断发生时，CPU 就会去查 IDT 的第 `N` 项，找到对应的处理函数地址并跳过去。

## 架构篇：四大核心组件的设计

你的代码巧妙地将整个系统分为了四个层级，各司其职：

### 1. 硬件通信层 (`io.h` + PIC 重映射)

- **痛点**：早期的 PC 架构中，可编程中断控制器（8259A PIC）默认把硬件中断（IRQ0~7）映射在了 `0x08~0x0F`，这**与 CPU 保留的内部异常冲突**。
- **解决**：在 `idt.c` 的 `pic_remap()` 中，通过向 `0x20` 和 `0xA0` 端口发送 ICW 指令，强制将硬件中断搬家到 **`32~47`**（即 `0x20~0x2F`），彻底解决冲突。

### 2. 数据结构层 (`idt.h`)

- **`idt_entry_t`**：8 字节的硬件标准结构。记录了：
  - **入口地址**：被拆成了低 16 位和高 16 位。
  - **段选择子**：固定填 `0x08`（告诉 CPU 跳转时切换到**内核代码段**）。
  - **属性属性**：固定填 `0x8E`（代表这是 32 位**中断门**，进入时硬件会自动关中断，防止嵌套崩溃）。
- **`registers_t`**：**软件栈镜像**。它的成员顺序与汇编压栈的顺序**完全逆序对应**。有了它，C 语言函数就能直接像读结构体一样，读取 CPU 崩溃瞬间的所有寄存器状态。

### 3. 汇编跳板层 (`idt_asm.asm`)

- **痛点**：C 语言函数不懂怎么保存 CPU 现场（不知道用 `pusha`），也不懂怎么用 `iret` 返回，更无法统一 Error Code 的栈布局。
- **解决**：写一段纯汇编作为“中介（Stub）”：
  1. 补齐 Error Code 和 中断号。
  2. 保存所有通用寄存器。
  3. **切换数据段（DS）到 `0x10`（内核数据段），确保 C 语言能安全寻址**。
  4. 带着栈指针（`push esp`）跳入 C 语言。

### 4. C 语言主控层 (`idt.c`)

- 负责把汇编 Stub 的地址填入 IDT 表，并通过 `lidt` 指令通告 CPU。
- 提供全局的分发器 `isr_handler`，根据传进来的中断号，调用具体的驱动逻辑，或者打印异常信息停机。

## 动态推演篇：`int $0x03` 的生死 1 微秒

当你执行 `__asm__ volatile("int $0x03");` 时，底层到底发生了什么？这是整个系统最精彩的流转：

### 【第一阶段：硬件魔法（纯 CPU 行为，无需写代码）】

1. CPU 收到 3 号中断信号。
2. CPU 查内部的 `IDTR` 寄存器，找到 IDT 表在内存中的位置。
3. CPU 取出 IDT[3] 的 8 字节描述符。
4. CPU 检查权限通过后，**自动执行硬件压栈**（此时使用的是 `boot.asm` 里分配的 16KB 内核栈）：
   - `push EFLAGS` (保存标志位)
   - `push CS` (保存旧的代码段)
   - `push EIP` (保存中断结束后的返回地址)
5. CPU 将 `CS` 寄存器替换为 `0x08`，将 `EIP` 替换为 `isr3` 的地址。**（控制权正式移交！）**

### 【第二阶段：汇编跳板（`idt_asm.asm`）】

1. 执行 `isr3`：
   - `cli` (确保关中断)
   - `push 0` (因为断点异常没有 ErrorCode，我们手动填 0 对齐栈)
   - `push 3` (压入中断号)
   - `jmp isr_common_stub`
2. 执行 `isr_common_stub`：
   - `pusha` (一口气压入 EAX~EDI 8个寄存器)
   - `push ds` (压入旧的数据段)
   - `mov ds, 0x10` **(手动将数据段切到内核数据段，为 C 语言护航)**
   - `push esp` **(极其巧妙：把当前的栈顶指针作为参数 `regs` 传给 C 函数)**
   - `call isr_handler`

### 【第三阶段：C 语言处理（`idt.c`）】

1. 进入 `isr_handler(registers_t* regs)`：
   - 此时 `regs->int_no` 正好等于 3。
   - 调用 `printk` 打印出 `[Exception] Breakpoint ...`。
   - C 函数执行完毕，遇到 `return`（或大括号结束）。

### 【第四阶段：原路返回（`idt_asm.asm`）】

1. 返回到 `isr_common_stub`：
   - `add esp, 4` (把之前传参的 esp 丢弃)
   - `pop ds` (恢复进入中断前的数据段)
   - `popa` (恢复所有通用寄存器)
   - `add esp, 8` (丢弃我们手动压入的 ErrorCode 和中断号)
2. **执行终极指令：`iret`**。
   - CPU 自动从栈顶弹出 EIP、CS、EFLAGS。
   - CPU 时空倒流，回到了 `kernel_main` 里 `int $0x03` 的下一行代码继续执行。
